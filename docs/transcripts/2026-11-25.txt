Give Postgres analytics a columnar read replica

First up, Mason gives a Postgres application another place to send its big analytical questions. It synchronizes selected tables and columns into DuckDB, then translates incoming Postgres queries for that columnar engine. The application still speaks Postgres SQL. In the team's demonstration, grouping ten million request rows takes fifteen point seven seconds on the primary and about point nineteen seconds on Mason, with the same answer. That's one published comparison, rather than a forecast for your dashboard. Developers could use Mason to query Postgres analytics while exploring a separate path for reports or agent questions. It runs as one Node.js process, and synchronization can happen on demand, through polling or through logical replication. The project explicitly says narrow primary-key lookups aren't its strength. Pick one expensive group-by from a test database, compare the answers, and measure how fresh the replica is when the underlying rows change.

Keep experimental attempts separately accessible

Turning to research agents, MLEvolver asks what an experiment-running agent should remember between attempts. The researchers separate two choices: how to preserve past experiments, and how to keep useful lessons. Across three models and two benchmark families, individually accessible attempt records beat a rolling summary. Context folding, which condenses each attempt into a short digest, performed best in all six settings. For lessons, deleting persistently unused ones helped more on average than merging them or making them permanent rules. The combined harness reached a reported seventy-two point seven percent medal rate on MLE-Bench Lite, ahead of AIDE and OpenEvolve under the same inference budget. Agent builders get a specific design to investigate: preserve the experiment history while pruning the advice nobody uses. Compare that with your current memory system on repeated optimization tasks. Inspect whether the agent can retrieve an earlier failure when it becomes relevant again.

Download a document parser for your own infrastructure

Over in document processing, LlamaIndex has released the weights for OCRia-1, its four-billion-parameter parsing model. The team describes it as handling complex tables, charts and difficult scans, and says the weights are available through Hugging Face and Ollama. That changes where you can experiment: the model can run on infrastructure you control. Developers building searchable archives could use OCRia-1 to parse documents locally, then feed the extracted material into their existing retrieval pipeline. The release has its own model license, so open weights shouldn't be read as an unrestricted licensing promise. There's no supported hardware requirement or accuracy comparison to give you here. A useful first evaluation is a small collection with known answers: a table with merged cells, a chart with labeled values, and a rough scan. Check whether the extracted relationships survive, especially before turning a tidy-looking output into searchable facts.

Turn proof counterexamples into runtime tests

At the correctness bench, Conao3 has published a Clojure investigation combining Lean proofs with differential testing. Small integer and bit-manipulation functions became Lean models. When a property failed, the author translated the counterexample into a Clojure input and reproduced the behavior in the original implementation. Larger collections were tested against Java collections instead. The author reports seventeen bugs they couldn't find in the project's issue tracker or community site, using Clojure one point twelve point seven and JDK twenty-one. Interestingly, three million differential-test operations found no mismatch in the HAMT itself; failures appeared in surrounding code and boundaries between mechanisms. Library maintainers could borrow this division of work: prove a small arithmetic property, then test how the surrounding system uses it. Follow one counterexample through the original runtime and proposed correction. The useful result is a reproducible failing input, with a precise account of the property it violates.

Put an adjustable workspace in a shareable URL

Closer to the interface, Sashay is a sliding-pane library with a nice answer to a familiar problem: your useful arrangement disappears when somebody else opens the application. Pane widths, open panes and expanded bars can fit into a short layout code in the URL. Developers building a document browser or inspection tool could use Sashay to share pane layouts, keeping a list beside the detail somebody needs to examine. Dragging a divider snaps it to simple fractions. Panes that run out of room fold under their neighbors, and phone layouts expose tabs. The site identifies version one point three, an MIT license, a dependency-free core and a React interface requiring React nineteen or newer. It also documents keyboard controls on every edge. Build a tiny list-and-detail view, squeeze it down to phone width, then send its layout link to another screen. See whether the arrangement still communicates what you wanted someone to inspect.

Run robot policies without loading PyTorch

Back from the break, ExecuTorch-TensorRT offers a smaller runtime path for robot policies written in PyTorch. With Torch-TensorRT two point fifteen and ExecuTorch one point six, you compile a model into an ExecuTorch program backed by TensorRT. The robot can then run it from C-plus-plus or Python without loading PyTorch. Operations TensorRT can't handle can still run on the GPU. The NVIDIA and Meta teams report fitting a three-point-six-billion-parameter policy on an eight-gigabyte Jetson Orin Nano, where eager PyTorch runs out of memory. Their GR00T one point seven example takes about two hundred milliseconds per action chunk. Robotics developers investigating onboard inference get a concrete deployment route to compare with their current export process. An action chunk contains a short plan, so that timing isn't a per-action measurement. Measure the complete loop with cameras and other models running too. Everything on that little board shares the same memory.

Let video codecs identify redundant model inputs

Turning to generated video, CodecOPSD borrows an idea from the machinery that compresses ordinary video. A generation model may receive reference images, depth maps or motion clips. All of those become input tokens, including plenty of repeated information. The researchers use a codec to identify redundant tokens, then train an adapter to work with the pruned inputs. Across sixteen conditioning modalities on their video diffusion model, they report removing sixty-six percent of condition tokens on average with almost no quality loss. Denoising becomes twice as fast in their tests, and cache memory falls by up to seventy-three percent in key-value-cache mode. Creative-tool researchers could investigate richer combinations of references within a smaller processing budget. Those figures concern the evaluated generation machinery, rather than an entire application's response time. Compare a sequence with one reference against the same sequence with several. Check whether removing repeated information preserves the small detail that made each reference useful.

Share a browser profile across concurrent sessions

Meanwhile, Browser Use has announced real-time profile synchronization across concurrent cloud browsers. The company says a login, cart, session and settings can follow the browsers as they run, without changes to existing code. For developers splitting an authenticated workflow across several browser workers, that could remove repeated sign-ins and stale copies of session state. The useful experiment is small: sign into a test account in one browser, change a harmless preference, and check whether a second running browser sees it. Shared state also creates an interesting coordination question. If two workers change the same cart or setting, what result does each observe? The announcement doesn't document conflict handling or independent reliability measurements. Start with workers that read different pages, then introduce one controlled state change. That gives you a way to examine synchronization before making concurrent actions depend on it.

Test which model units support one next-token answer

For a look inside a small model, Open Interpretability Explain traces a next-token answer through neurons and attention heads. It first records typical activations over twenty thousand tokens. Then it ranks units by how unusually they activate and how sensitive the chosen answer is to them. Crucially, it also switches units off to test those estimates. In the project's Pythia seventy-million demonstration, keeping eighty-six explained units while placing other neurons at baseline restores eighty-one point nine percent of the probability assigned to the answer, sky. Random neuron sets restore thirteen percent on average. Interpretability learners get a concrete example of moving from an attribution score to an intervention. This is a small-model demonstration with a young explanation registry, rather than a complete account of an assistant's reasoning. Explore one prompt, inspect the units it highlights, and compare the explanation with what happens when those units are actually changed.
